# AWS デプロイ手順（AWS-Optimize ブランチ）

JAWS-UG佐賀 ワークショップ用。管理者がシャッフルを実行し、参加者は公開URLで結果を閲覧する。

## 構成

| 役割 | サービス |
|---|---|
| 画面配信 + API | API Gateway HTTP API (`$default` ステージ) → Lambda |
| データ保存 | DynamoDB（1イベント = 1アイテム） |
| 管理者認証 | Cognito User Pool（USER_PASSWORD_AUTH） |
| リアルタイム更新 | AppSync Events（チャンネル `/team-drawer/shuffle`） |

チーム分けアルゴリズムと佐賀弁チーム名（`src/api.ts` の `SAGA_WORDS` / `pickRandomSagaNames`）は元のまま。

## 前提

- Node.js 20 以上
- AWS 認証情報が設定済み（`aws sts get-caller-identity` が通ること）
- 対象リージョンで CDK ブートストラップ済み

```bash
npm install
npx cdk bootstrap aws://<ACCOUNT_ID>/ap-northeast-3   # 初回のみ
```

## デプロイ

管理者パスワードは環境変数で渡す（リポジトリに平文で置かない）。

```bash
ADMIN_PASSWORD='YourStrongPassw0rd' \
ADMIN_EMAIL='admin@example.com' \
npm run cdk:deploy
```

パスワード要件: 8文字以上／大文字・小文字・数字をそれぞれ1文字以上。

> ⚠️ **必ず「使い捨て」のパスワードを使うこと。他で使っているものを流用しない。**
> 指定したパスワードは CloudFormation テンプレートとカスタムリソース Lambda の
> CloudWatch Logs に平文で残る（理由と判断は下記「AGY レビューへの対応」を参照）。
> このイベント専用の捨てパスワードにしておけば実害はない。

デプロイ完了後、`ParticipantUrl` と `AdminUrl` が出力される。

> `cdk bootstrap` もアプリを合成するため、当初は `app.ts` の
> パスワード必須チェックがブートストラップまで巻き添えで失敗させていた。
> 現在は「パスワード未設定ならスタックを生成せず、案内を出して終了」する
> 実装にしてあるので、ブートストラップに `ADMIN_PASSWORD` は不要。

## リージョンの切り替え

既定は **ap-northeast-3 (Osaka)**。AppSync Events が未提供などで失敗した場合は東京へ:

```bash
APP_REGION=ap-northeast-1 ADMIN_PASSWORD='...' npm run cdk:deploy
```

切り替え箇所は `cdk/bin/app.ts` の `region` のみ。

## 撤収

```bash
npm run cdk:destroy
# 別リージョンに残っている場合
APP_REGION=us-east-1 npm run cdk:destroy
```

## フェーズ3: セキュリティ自己レビューで見つけた点

引き渡し前に差分を見直して、当日の運用リスクを2つ潰した。

### 1. AppSync の API キーは公開情報である

参加者画面が購読するために `/api/config` で API キーを返しており、第三者も
同じチャンネルに publish できる。ただし**偽データが表示されることはない**:
参加者画面は通知をトリガーにするだけで、中身は必ず `/api/events/{code}` から
取り直しているため。

残る影響は「通知を連打してバックエンドを叩かせる」こと。フロント側で
**再取得を1秒に1回までスロットル**して緩和した（末尾の通知は取りこぼさない）。

publish を IAM 認証に限定すれば根本的に塞げるが、Lambda 側で SigV4 署名が必要になる。
影響が「再取得の誘発」に留まることと、単発イベントであることを踏まえて採用しなかった。

### 2. 参加者登録 API が無認証

元の仕様どおり参加者の自己登録を許しているが、無制限だと DynamoDB の
アイテムサイズ上限(400KB)に達してイベントの状態そのものが壊れうる。

**参加者数の上限を500名**とし、超える場合は全件拒否するようにした
（中途半端に保存されると状況が分かりにくいため all-or-nothing）。
管理者のシャッフル実行時も同じ上限で検証する。

### 3. 任意のイベントコードで無制限に書き込めた（後日の再レビューで発見）

`POST /api/events/{任意のコード}/participants` は無認証のため、コードを変えるだけで
DynamoDB アイテムを無制限に作成できた。公開URLなのでストレージと課金の
濫用につながる。

このスタックは単発イベント用なので、**扱うイベントコードを1つに固定**し
(`EVENT_CODE` 環境変数、既定 `JAWS-SAGA`)、それ以外は読み書きとも 404 を返すようにした。

あわせて **API Gateway にスロットリング**を設定した（rate 500 rps / burst 1000）。
参加者300名が3秒ポーリングしても 100rps 程度なので通常利用には十分な余裕があり、
暴走時の課金上限として機能する。

## フェーズ6: 実機デプロイで判明した問題と参加フローの追加

### 1. ログインできない → デプロイ時の ADMIN_EMAIL のタイポ

`t.shibao@midnigt480.com`（h 抜け）でデプロイされており、
`t.shibao@midnight480.com` でログインすると `UserNotFoundException` になっていた。

Cognito の `InitiateAuth` は認証不要 API なので、直接叩いて切り分けた。

```
USERNAME=t.shibao@midnight480.com → UserNotFoundException
USERNAME=t.shibao@midnigt480.com  → 成功（トークン取得）
```

この調査で、**恒久パスワード設定は正しく動作**しており、
**AppSync Events も大阪リージョンで利用可能**であることが確認できた。

### 2. ログインエラーの原因が分からなかった（実装の欠陥）

`handleLogin` が全ての Cognito 例外を
「メールアドレスまたはパスワードが正しくありません」に潰していたため、
`UserNotFoundException`（設定ミス）と単なるパスワード誤りが区別できなかった。

エラー種別ごとにメッセージを分けた。管理者1名の単発イベント用途なので、
ユーザー列挙のリスクより当日に原因を追えることを優先している。

### 3. 参加者が参加する導線が無かった

main ブランチには存在したが AWS 版で落ちていた機能を復活させた。

| 機能 | 内容 |
|---|---|
| 会場表示モード `/e/{code}/display` | QRコード＋参加用URL＋チーム結果。プロジェクタ用 |
| 参加者の自己登録 | 参加者画面に名前入力を追加（API は既存の `POST /participants` を利用） |
| 自分のチームの強調表示 | 端末に保存した表示名と突き合わせ、枠線と「← あなた」を表示 |

当日の流れ:
プロジェクタに `/e/{code}/display` を出す → 参加者がQRをスキャン →
名前を登録 → 管理者がシャッフル実行 → 全員の画面に反映。

QR は main と同じく外部サービス（api.qrserver.com）で生成している。
読み込めなかった場合に備えて参加用URLも大きく表示している。

### 4. 入力中の文字が3秒ごとに消えるバグ（ブラウザ確認で発見）

3秒ごとの自動更新が参加登録フォームごと DOM を作り直しており、
**参加者が名前を入力している最中に文字とフォーカスが失われていた**。
当日ほぼ確実に踏むバグ。状態（未登録／登録済み）が変化したときだけ
描き直すようにして修正した。

## フェーズ7: くじ引き方式へ変更（main の参加体験に戻す）

フェーズ6 で「参加者が名前を登録 → 管理者がシャッフル実行」にしていたが、
main は**管理者の操作が一切ない**方式だった。当日の運営を考えても
管理者がボタンを押すタイミングに依存しないほうが良いため、
セルフ抽選に戻した。

### 方式

参加者が名前を入れて「くじを引く」→ **その場でチーム確定**。管理者操作は不要。

main との違いは枠の扱い。main は事前に決めた枠（例: 4チーム [4,4,5,5]）を
埋める方式で、枠が尽きると `409 空き枠がありません` で参加できなくなっていた。
ここでは**上限を設けず、その時点で一番人数が少ないチームに入れる**（同数なら抽選）。
これで事前の人数見積もりが不要になり、遅刻者もそのまま参加できる。

チーム数は `TEAM_COUNT` 環境変数（既定 4）。最初の1人がくじを引いた時点で
佐賀弁のチーム名とコメントを確定させ、以降はそこに追加していく。

### 同時アクセス対策（楽観ロック）

40人が一斉にQRを読んでくじを引く場面では、単純な読み出し→上書きだと
更新が失われて参加者が消える。DynamoDB のアイテムに `version` を持たせ、
`ConditionExpression` で「誰も書き換えていないときだけ成功」させ、
衝突したら読み直して再試行するようにした（最大8回、ランダム待機）。

`test/handler.test.ts` で **20人が同時にくじを引いても全員が取りこぼされない**
ことを検証している。

### 管理画面の位置づけ変更

参加者リストは自動で埋まるため、管理者の操作は通常不要。
シャッフルボタンは「全員を引き直す」（＝やり直し用）として残している。

## フェーズ8: 大阪での実機確認と、そこで見つけた不具合

`https://7k4eys2z5d.execute-api.ap-northeast-3.amazonaws.com` にデプロイし、
スマホでQRを読み取ってくじを引くところまで通ることを確認した。

| 確認項目 | 結果 |
|---|---|
| 管理者ログイン（Cognito） | ✅ |
| 会場表示モードのQRコード表示 | ✅ |
| スマホでQR読み取り→名前入力→チーム確定 | ✅ |
| AppSync Events が大阪で使えるか | ✅ エンドポイント生成・稼働 |

### デプロイ時に踏んだ問題

1. **`cdk bootstrap` が `app.ts` の throw で巻き添え停止**（フェーズ間で修正済み）
2. **`export` した認証情報が引き継がれない** — セッション上のコマンドは
   1回ごとに新しいシェルで実行されるため、`export` した環境変数が次のコマンドに
   残らない。認証情報とデプロイを1コマンドにまとめる必要があった。
3. **`Unable to resolve AWS account to use`** — `env.account` に
   `CDK_DEFAULT_ACCOUNT` を要求していたため、認証情報が解決できないと
   原因の分かりにくいエラーで止まっていた。`account` の指定自体をやめ、
   デプロイ時の認証情報から決まるようにした。
4. **`ADMIN_EMAIL` のタイポが再度反映されなかった** — 上記2が原因。
   Cognito ユーザー名としてしか使わず、`messageAction: SUPPRESS` で
   メール送信もしないため、実害はないと判断してそのままにした。

### 実機確認で見つけた不具合: リセット後に参加者が二重登録される

`handleResetAssignments` がチーム分けだけを消して**参加者リストを消していなかった**。
この状態で同じ人がもう一度くじを引くと、参加者リストに同じ名前が二重に積まれる。
**本番前にリセットして仕切り直す運用で必ず踏む**ため修正した。

- リセット時に `participants` も空にする
- くじ引き側でも重複を弾く（防御的に二重化）

| イベント取得 | ✅ 200 / 37〜53ms |

> HAR の `content.text` は base64 エンコードされている。デコードせずに
> 中身を検索すると「機能が入っていない」と誤判定するので注意。

### リセットの不具合が実データで裏付けられた

`10:48:40` の `GET /api/events/JAWS-SAGA` が
`teams: []` かつ `participant_count: 6` を返している。
これはフェーズ8で修正した「リセットがチーム分けだけ消して参加者を残す」挙動そのもの。

### 新たに発見: 管理画面が参加者の増加に追従しない

管理画面は開いた時点の参加者リストをテキストエリアに読み込んだきり更新せず、
「全員を引き直す」はそのテキストエリアの内容で**サーバ側の参加者を置き換える**。

そのため **管理画面を開いた後にくじを引いた人は、引き直すと消える**。
開場中はずっと人が増えるため当日必ず踏む。

修正: 管理画面も3秒ごとにサーバへ追従させる。ただし
「管理者が手で編集した場合」と「入力中（フォーカス中）」は上書きしない。

ローカルで両方の挙動を実際に確認した。

- 管理画面を開いた後にくじを引いた人 → テキストエリアに自動で追加される
- 管理者が手で書き換えた内容 → ポーリングで上書きされない

### AppSync WebSocket について

HAR に WebSocket のエントリは無かったが、これは**管理画面の HAR だから**。
`setupAppSyncRealtime()` は参加者画面と会場表示モードでしか呼ばれない。
（加えて Chrome の HAR エクスポートは WebSocket フレームを含まない）
確認するなら参加者画面のコンソールで
`AppSync Events 購読開始: /team-drawer/shuffle` が出るかを見る。

## AGY レビューへの対応

`docs/AGY_REVIEW.md`（commit `e45ac48`）の指摘を検証した結果。

### 指摘は正しかった: 管理者パスワードの平文記録

`ADMIN_PASSWORD='SuperSecret123'` で `cdk synth` して確認したところ、
テンプレート内に**平文で2回**出現した（`AwsCustomResource` の `Create` と `Update`）。

```
$ grep -c "SuperSecret123" cdk.out/TeamDrawerStack.template.json
2
```

さらに `AwsCustomResource` の既定ログ設定は `Logging.all()` で、これは
**イベントオブジェクトごと出力**するため、露出箇所は2つある。

1. CloudFormation テンプレート（スタック履歴に永続的に残る）
2. カスタムリソース Lambda の CloudWatch Logs

なお **CloudTrail への記録という部分は誤り**。Cognito は `AdminSetUserPassword` の
`Password` を機密フィールドとして秘匿するため、CloudTrail には出力されない。

#### 採った対策: 使い捨てパスワード運用（コード変更なし）

このリスクの本体は「他所で使っているパスワードの使い回し」である。
専用の捨てパスワードを使えば、露出しても失われるものは
「このチーム分け画面の管理権限」だけで、実害はほぼ無い。

検討して**採らなかった**案:

| 案 | 採らなかった理由 |
|---|---|
| Secrets Manager で自動生成し、専用 Lambda が ARN 経由で読む | テンプレートにもログにも残らない正しい解だが、**未テストのカスタムリソースを増やす**ことになる。まだ大阪への初回デプロイが成功していない段階で、デプロイ失敗要因を持ち込むほうがリスクが高いと判断 |
| CDK からパスワード設定を外し、デプロイ後に手動で1コマンド | パスワードはどこにも残らないが、要件の「`cdk deploy` 一発」から後退する |

ワークショップ後も継続運用するなら、Secrets Manager 版に切り替えるのが本筋。

### レビュー自体の限界（記録として）

1. **古いコミットが対象**。レビューは「35件パス」と記載しているが、当時点の最新は
   37件（`be06e65`）。**イベントコードの固定と API Gateway スロットリングが
   レビュー対象に入っていない**。
2. **既知の脆弱性を検出できていない**。セクション4で `MAX_PARTICIPANTS` には
   触れているが、同じく無認証だった「任意のイベントコードで無制限に書き込める」
   問題（`be06e65` で修正済み）には言及がない。これは実際に再現確認した実在の穴だった。

したがって、このレビューの「合格」判定は**独立した検証というより、
自己レビューで潰した後の状態の追認**として受け取るのが妥当。

## デプロイ時に注意が必要な残リスク

1. **AppSync Events の Osaka 提供状況** — 未確認。`cdk deploy` で失敗したら
   `APP_REGION=ap-northeast-1` で東京へ。
2. **AppSync Events の WebSocket** — プロトコルはドキュメント準拠で実装したが実機未検証。
   仮に接続できなくても参加者画面は3秒ポーリングで結果を表示できる。
   ブラウザのコンソールに `AppSync Events 購読開始:` が出れば成功。
3. **旧 us-east-1 スタックの撤収** — 別途 `APP_REGION=us-east-1 npx cdk destroy` が必要。
4. **AWS アクセスキーのローテーション** — チャットに平文で共有されたキーは無効化すること。
5. **管理者パスワードは使い捨てを使う** — CloudFormation テンプレートに平文で残る。
   詳細は「AGY レビューへの対応」を参照。

## 設計メモ

- **DynamoDB を使う理由**: Lambda の `/tmp` は実行環境ごとに独立しており、複数コンテナに分散すると管理者が書いた結果を参加者が読めない。当日は参加者が一斉アクセスするため確実に分散する。
- **HTTP API を使う理由**: REST API は URL が `/prod/...` になり、フロントの絶対パス（`/api/...`, `/styles.css`）が届かなくなる。`$default` ステージならパスにステージ名が入らない。
- **Cognito の恒久パスワード**: `CfnUserPoolUser` だけでは `FORCE_CHANGE_PASSWORD` のままログインできないため、`AwsCustomResource` で `AdminSetUserPassword` を実行している。
- **AppSync Events のフォールバック**: 参加者画面は WebSocket 購読に加えて 3 秒ポーリングも併用しているため、リアルタイム通知が落ちても結果は反映される。
